# INTENT.md

## Objective

Создать framework-agnostic TypeScript веб-клиент для opencode-сервера поверх `@opencode-ai/sdk`, покрывающий весь документированный HTTP + SSE API через типизированные фасады, и работающее на его основе демо-веб-приложение (чат и дашборд), чтобы любой браузерный UI мог общаться с работающим opencode-сервером без ручного написания HTTP-вызовов и без пропущенных endpoint'ов.

## Strategy

- Клиент строится как тонкий слой фасадов над SDK-клиентом (`createOpencodeClient`): один ресурс сервера = одна namespace-группа типизированных методов (`project`, `session`, `config`, `mcp`, `tui`, …).
- Типы запросов/ответов переэкспортируются из SDK, а не изобретаются заново — поверхность держится в шаге от схемы сервера.
- Единая нормализация ошибок: SDK-ответы `{ data | error }` превращаются в отклонённые типизированные `OpencodeClientError` (status + message + raw).
- SSE-события отдаются как cancelable async iterable (`client.events()` / `client.subscribe()`).
- Демо-приложение (React + Vite) потребляет пакет напрямую через типизированный клиент (`web/src/lib/api.ts`), показывая живые данные сервера.
- Изменения ведутся через OpenSpec: specs → tasks → архив; каждая новая возможность фиксируется как delta-спек.

## Trade-offs

- **Полная зависимость от одного SDK** (`@opencode-ai/sdk` pinned `1.18.15`): новые endpoint'ы сервера появятся только после апгрейда SDK. Принято: фасады тонкие, апгрейд сводится к typecheck.
- **Отказ от собственного транспорта** в пользу SDK: меньше контроля над HTTP-слоем, зато нет дублирования и дрейфа маршрутов.
- **Пакет поставляет сырой TypeScript без build-шага** (`exports` → `./src/index.ts`): потребитель обязан использовать TS-aware bundler (Vite, esbuild, tsup). Принято ради простоты дистрибуции.
- **`OPENCODE_BASE_URL` не читается в браузерах** → явный `baseUrl` обязателен для нестандартных деплоев; env — только Node-удобство.
- **SSE из браузера на `localhost:54321` может упираться в CORS** → base URL полностью конфигурируем, требования к CORS документируются.
- **Нормализация ответов может быть ошибочной в тонких местах** → централизована в фасадах и покрыта тестами по каждому ресурсу.

## Desired outcomes

- Каждый документированный endpoint сервера доступен через типизированный фасад (`client.<resource>.<method>`).
- Каждый endpoint из `openspec/specs/web-client/spec.md` покрыт тестом (задача 12.5).
- `npm run typecheck` и `npm test` проходят; экспортируемая поверхность совпадает с SDK `OpencodeClient` route-by-route.
- SSE-стрим доставляет события, отменяется через `abort()`/`return()` и не «висит молча» при ошибках.
- Демо-приложение (Chat + Dashboard) работает против живого сервера и отображает реальные данные.

## Health metrics

- Покрытие endpoint'ов: отсутствие «дыр» между документированным API сервера и поверхностью фасадов.
- `npm run typecheck` и `npm test` зелёные (bun test + tsc --noEmit).
- Зафиксированная версия SDK; дрейф поверхности (появление/исчезновение методов) отслеживается и документируется при апгрейде.
- Демо-приложение запускается без ошибок подключения к локальному серверу.

## Constraints

- **Единственная runtime-зависимость** — `@opencode-ai/sdk` (pinned `1.18.15`); никаких новых runtime-зависимостей.
- **Ядро framework-agnostic**: в `src/` никаких React/Vue/компонентных библиотек; UI живёт только в `web/`.
- **Не переписывать транспорт SDK** — SDK остаётся единственным HTTP/SSE-движком.
- **Без аутентификации поверх API сервера**: никакого хранения токенов/авторизации в клиенте.
- **Zero breaking changes к серверу**: клиент только зеркалит API сервера.
- **Без build-шага** для пакета: `exports` указывает на исходный TS.

## Stop rules

- Прекращать работу, если скоуп выходит за рамки «клиент для документированного API сервера» (UI-фреймворки, роутинг, стор, компонентная библиотека — не-цели).
- Не добавлять endpoint'ы, отсутствующие в документированном API/SDK.
- Не менять API сервера и не расширять фасады за пределы его контракта.
- Если фасады начинают дублировать поведение SDK сверх нормализации — остановиться и пересмотреть подход.
